# Board Project FrontEnd 1차 작업 정리

- **작업 일자:** 2026-10-12
- **작업 범위:** React 화면 기본 구성, 회원가입·로그인 API 연결, JWT 기반 로그인 상태 관리
- **프로젝트 경로:** `front/`
- **상태:** 회원가입 및 로그인이 정상 동작하는 것을 사용자 실행 환경에서 확인함. 자동화된 프론트엔드 테스트 및 전체 빌드 결과는 별도로 확인하지 않음.

## 1. 작업 목표

Vite 기본 예제 화면을 Board Project에 맞는 프론트엔드로 교체하고, Spring Boot 백엔드에 구현되어 있는 회원가입·로그인 API를 연결한다. 로그인 후에는 JWT를 이용해 보호된 화면에 접근할 수 있도록 기본 인증 상태 관리 구조를 마련한다.

이번 단계에서는 게시판·게시글·댓글 등 실제 콘텐츠 조회 및 작성 기능은 아직 구현하지 않는다.

## 2. 사용 기술

| 구분 | 기술 | 용도 |
|---|---|---|
| UI | React | 화면 및 컴포넌트 구성 |
| 개발 서버·번들링 | Vite | 로컬 개발 및 빌드 환경 |
| 라우팅 | React Router | 페이지 이동 및 경로 보호 |
| HTTP 통신 | Axios | 백엔드 API 요청, 인증 헤더 및 공통 오류 처리 |
| 인증 상태 | React Context API | 로그인 사용자 정보 및 로그인 상태 공유 |
| 인증 토큰 저장 | `localStorage` | 새로고침 이후 토큰을 다시 확인하기 위한 임시 저장 방식 |
| 백엔드 연결 | Vite proxy | 프론트의 `/api` 요청을 `http://localhost:8080`으로 전달 |

기존 `front/package.json`, `front/package-lock.json`, `front/vite.config.js`는 유지하고 이미 설치된 React, React Router, Axios를 활용한다.

## 3. 구현된 화면 및 경로

| 경로 | 화면 | 접근 정책 | 설명 |
|---|---|---|---|
| `/` | 홈 화면 | 누구나 접근 | 서비스 소개 및 회원가입·로그인 링크를 표시한다. 로그인 상태에 따라 대시보드 링크를 보여준다. |
| `/signup` | 회원가입 | 비로그인 사용자 | 아이디, 닉네임, 선택 이메일, 비밀번호, 비밀번호 확인 입력을 제공한다. |
| `/login` | 로그인 | 비로그인 사용자 | 아이디와 비밀번호를 입력하고 백엔드에 로그인 요청을 보낸다. |
| `/dashboard` | 대시보드 | 로그인 필요 | 로그인 사용자 정보와 인증 상태를 표시한다. 다음 단계에서 게시판 기능을 연결할 자리다. |
| 그 외 | 404 화면 | 누구나 접근 | 존재하지 않는 경로에 안내 화면을 표시한다. |

로그인 상태에서 `/login` 또는 `/signup`에 접근하면 대시보드로 이동한다. 비로그인 상태에서 `/dashboard`에 접근하면 로그인 화면으로 이동하도록 구성했다. 로그인 전 방문하려던 경로가 있으면 로그인 이후 해당 경로로 돌아가도록 한다.

## 4. 주요 파일 구조

```text
front/
├─ index.html
└─ src/
   ├─ main.jsx
   ├─ App.jsx
   ├─ App.css
   ├─ index.css
   ├─ api/
   │  ├─ client.js
   │  └─ authApi.js
   ├─ auth/
   │  └─ AuthContext.jsx
   ├─ components/
   │  ├─ AppLayout.jsx
   │  └─ RouteGuards.jsx
   └─ pages/
      ├─ HomePage.jsx
      ├─ SignupPage.jsx
      ├─ LoginPage.jsx
      └─ DashboardPage.jsx
```

### 파일별 역할

- **`main.jsx`**: `BrowserRouter`와 `AuthProvider`를 구성해 하위 화면에서 라우팅과 인증 상태를 사용할 수 있게 한다.
- **`App.jsx`**: 화면 경로를 정의하고 홈·회원가입·로그인·대시보드·404 페이지를 연결한다.
- **`AppLayout.jsx`**: 상단 메뉴, 현재 사용자 표시, 로그인/로그아웃 메뉴, 공통 푸터를 제공한다.
- **`RouteGuards.jsx`**: 인증 초기 확인 중에는 로딩 화면을 표시하고, 로그인 여부에 따라 접근 가능한 경로를 제한한다.
- **`AuthContext.jsx`**: 로그인, 로그아웃, 앱 시작 시 기존 토큰 확인, 사용자 정보 상태 관리를 담당한다.
- **`api/client.js`**: Axios 인스턴스, 공통 API 경로, JWT 헤더, 401 응답에 대한 공통 처리를 담당한다.
- **`api/authApi.js`**: 회원가입·로그인·현재 사용자 확인 API 함수를 모아 둔다.
- **`pages/HomePage.jsx`**: 서비스 소개 및 회원가입·로그인 진입 화면이다.
- **`pages/SignupPage.jsx`**: 회원가입 입력과 기본 검증, 성공·실패 메시지를 처리한다.
- **`pages/LoginPage.jsx`**: 로그인 입력과 인증 요청, 성공 후 이동, 실패 메시지를 처리한다.
- **`pages/DashboardPage.jsx`**: 로그인된 사용자 정보를 보여 주고 이후 게시판 기능을 넣을 기본 화면이다.
- **`App.css`, `index.css`**: 공통 레이아웃, 색상, 인증 폼, 카드, 버튼 및 반응형 스타일을 관리한다.
- **`index.html`**: 한국어 페이지 메타데이터와 문서 제목을 설정한다.

## 5. 백엔드 API 연동

### 5.1 회원가입

- **요청:** `POST /api/auth/signup`
- **요청 본문 예시:**

```json
{
  "username": "sampleuser",
  "password": "sample-password",
  "nickname": "샘플 사용자",
  "email": "sample@example.com"
}
```

이메일은 선택 항목이다. 입력하지 않으면 프론트엔드는 `null`을 전달한다.

- **성공 응답 예시:**

```json
{
  "userId": 1
}
```

회원가입 성공 후 로그인 화면으로 이동하고 완료 안내 메시지를 표시한다. 회원가입 시 자동 로그인은 수행하지 않는다.

### 5.2 로그인

- **요청:** `POST /api/auth/login`
- **요청 본문 예시:**

```json
{
  "username": "sampleuser",
  "password": "sample-password"
}
```

- **성공 응답 필드:**

```json
{
  "accessToken": "<JWT>",
  "userId": 1,
  "username": "sampleuser",
  "nickname": "샘플 사용자",
  "role": "USER"
}
```

실제 토큰 값과 ID는 서버 응답에 따라 달라진다. 프론트엔드는 토큰이 응답에 포함되어 있는지 확인하고, 토큰을 저장한 후 보호 API인 `/api/auth/me`를 호출해 인증 여부를 확인한다. 인증 확인이 성공하면 사용자 상태를 저장하고 대시보드로 이동한다.

### 5.3 로그인 사용자 확인

- **요청:** `GET /api/auth/me`
- **인증 헤더:** `Authorization: Bearer <JWT>`
- **현재 백엔드 응답:**

```json
{
  "username": "sampleuser"
}
```

현재 백엔드의 `/api/auth/me`는 사용자 이름만 반환한다. 따라서 로그인 응답의 `userId`, `nickname`, `role` 값은 프론트엔드 사용자 상태에 함께 보관하고, 세션 복원 시 `/api/auth/me` 응답의 사용자 이름으로 서버 인증을 다시 확인한다.

## 6. 인증 상태 및 토큰 처리

### 로그인

1. 사용자가 로그인 폼을 제출한다.
2. `authApi.login()`이 `/api/auth/login`을 호출한다.
3. 응답에 `accessToken`이 있으면 `localStorage`에 저장한다.
4. 저장된 토큰을 포함해 `/api/auth/me`를 호출한다.
5. 인증이 성공하면 사용자 정보를 `AuthContext`에 저장하고 대시보드로 이동한다.
6. 로그인 또는 토큰 확인이 실패하면 오류 메시지를 보여 주고 인증 데이터를 정리한다.

### 새로고침 후 세션 복원

1. 앱이 시작되면 `AuthProvider`가 저장된 토큰을 확인한다.
2. 토큰이 있으면 `/api/auth/me`를 호출한다.
3. 서버가 토큰을 받아들이면 저장된 사용자 표시 정보를 복원한다.
4. 토큰이 유효하지 않거나 요청이 실패하면 저장된 인증 데이터를 삭제하고 비로그인 상태로 처리한다.

### 로그아웃

로그아웃 버튼을 누르면 저장된 토큰과 사용자 정보를 삭제하고 홈 화면으로 이동한다. 현재 방식은 서버의 별도 로그아웃 API를 호출하지 않는 클라이언트 측 로그아웃이다.

### 공통 API 처리

- Axios의 `baseURL`은 `/api`로 설정한다.
- 저장된 토큰이 있으면 요청 헤더에 `Authorization: Bearer <token>`을 자동으로 추가한다.
- 로그인·회원가입 요청을 제외한 API에서 `401 Unauthorized`가 발생하면 로컬 인증 정보를 삭제하고 인증 상태를 비운다.
- 서버 오류 응답에 `message`가 있으면 이를 우선 표시한다. 그렇지 않으면 일반 오류 메시지를 사용한다.
- 요청 타임아웃은 10초로 설정되어 있다.

## 7. 회원가입 입력 검증

프론트엔드 폼은 다음과 같은 기본 입력 제약을 적용한다. 서버에서도 검증하므로 프론트 검증은 사용자 편의를 위한 1차 검사이며, 보안 검증을 대체하지 않는다.

| 필드 | 규칙 |
|---|---|
| 아이디 | 필수, 4~50자 |
| 닉네임 | 필수, 2~50자 |
| 이메일 | 선택, 이메일 형식, 최대 100자 |
| 비밀번호 | 필수, 8~100자 |
| 비밀번호 확인 | 비밀번호와 일치해야 함 |

비밀번호 확인은 프론트에서 검사하며, 요청 본문에는 `passwordConfirm`을 보내지 않는다.

## 8. 로컬 실행 방법

### 사전 조건

- MariaDB와 백엔드 설정이 정상이어야 한다.
- Spring Boot 백엔드가 기본 개발 포트 `8080`에서 실행 중이어야 한다.
- Node.js 및 npm이 설치되어 있어야 한다.

### 프론트엔드 실행

프로젝트 루트에서 새 터미널을 열고 실행한다.

```powershell
cd front
npm ci
npm run dev
```

Vite가 출력한 로컬 주소를 브라우저에서 연다. 기본 설정에서는 일반적으로 `http://localhost:5173`을 사용한다.

### API 프록시

기존 `front/vite.config.js`에는 아래와 같은 프록시가 설정되어 있다.

```js
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true,
    },
  },
}
```

따라서 브라우저 프론트엔드의 `/api/auth/login` 요청은 개발 중 Spring Boot 서버의 `http://localhost:8080/api/auth/login`으로 전달된다. 프론트에서 API 주소를 직접 `localhost:8080`으로 작성하지 않도록 공통 클라이언트를 사용한다.

## 9. 확인 결과와 테스트 항목

### 확인된 사항

- 사용자가 실행 환경에서 회원가입과 로그인이 정상 동작한다고 확인했다.
- 회원가입·로그인 연동은 기존 Spring Boot 인증 API를 사용하며, 백엔드 코드를 변경하지 않았다.

### 추가로 확인할 수동 테스트

- [ ] 회원가입 필수 항목을 비워 제출했을 때 브라우저 입력 검증이 작동하는가?
- [ ] 비밀번호와 비밀번호 확인이 다르면 요청이 전송되지 않는가?
- [ ] 같은 아이디 등 중복 정보가 있을 때 백엔드 오류 메시지가 보이는가?
- [ ] 잘못된 비밀번호로 로그인했을 때 실패 메시지가 표시되는가?
- [ ] 로그인 성공 후 대시보드에 사용자 정보가 표시되는가?
- [ ] 로그인 상태에서 새로고침해도 서버 인증 확인 후 세션이 복원되는가?
- [ ] 비로그인 상태에서 `/dashboard`에 직접 접근하면 로그인 화면으로 이동하는가?
- [ ] 로그아웃 후 보호된 화면에 다시 접근할 수 없는가?
- [ ] 만료되거나 유효하지 않은 토큰으로 보호 API를 호출하면 로그아웃 상태로 정리되는가?

위 체크리스트는 검증을 권장하는 항목이며, 체크하지 않은 항목을 테스트 완료로 간주하지 않는다. 현재 단계에서 별도의 프론트엔드 자동화 테스트 코드는 추가하지 않았다.

## 10. 보안 및 현재 한계

1. **토큰 저장 위치:** 현재 JWT를 `localStorage`에 저장한다. 스크립트 삽입(XSS) 취약점이 발생하면 토큰이 노출될 수 있으므로, 사용자 입력 출력 처리와 의존성 보안을 신경 써야 한다. 운영 수준에서는 HttpOnly·Secure 쿠키 등 대안을 검토할 수 있으며, 인증 방식 변경은 백엔드 변경도 필요할 수 있다.
2. **세션 갱신:** 현재 별도의 Refresh Token 또는 토큰 갱신 흐름은 구현하지 않았다. 토큰 만료 후에는 다시 로그인해야 한다.
3. **현재 사용자 API:** `/api/auth/me`는 현재 사용자 이름만 반환한다. 사용자 정보를 더 신뢰성 있게 복원하려면 추후 백엔드에서 닉네임·권한 등의 필드를 포함하도록 확장할 수 있다.
4. **인가 판단:** 화면에서 특정 메뉴를 숨기거나 경로를 차단하는 것만으로는 보안을 보장할 수 없다. 실제 권한 검사는 계속 백엔드에서 수행해야 한다.
5. **콘텐츠 기능:** 게시판 목록·상세, 게시글 작성·수정·삭제, 검색, 댓글, 좋아요, 첨부파일 화면은 아직 이 단계에 포함되지 않는다.
6. **빌드와 자동화 테스트:** 사용자 환경에서 회원가입과 로그인 성공이 확인되었지만, 이 문서 작성 환경에서 `npm run build` 또는 실제 백엔드 연결 테스트를 실행한 것은 아니다.
